## Themes

Three themes account for effectively all clusters:

### T1 — `Serializer.fromJSON`: a non-string `$class` crash (1,694 divergences → now 0 unresolved; resolved via #156)

TS's `Serializer.fromJSON` reaches `ModelUtil.getShortName`/`getNamespace`
(`packages/concerto-core/src/modelutil.ts:119,143`), which calls
`fqn.lastIndexOf('.')` on the instance's `$class` with no type check. A mutated,
non-string, *scalar* `$class` (`true`, a number — anything without its own
`.lastIndexOf`) makes V8 throw `TypeError: fqn.lastIndexOf is not a function` — a TS
bug (no counterpart in the spec).

Rust's `instance/serializer.rs` and `instance/populator.rs`
(`accordproject/concerto-rust`, both reached from the P4-10 Serializer fast path)
explicitly check `$class`'s type and raise a plain `Error: a $class that is not a
string: <value>` — arguably *more* correct than TS, but not byte-for-byte the same
class or message, so every such case diverged.

**Resolved: accordproject/concerto-rust#156. Maintainer decision (2026-09-25): keep
Rust's clearer error; do not port the TS crash** — an explicit, approved exception to
PORTING.md 7.3's "no improvements" rule, recorded as `DIVERGENCES.md` DV-015
(category `maintainer-accepted`, a new category added to PORTING.md 7.3 for exactly
this kind of sign-off). `migration/fuzz/lib/expected-divergences.js` now matches this
exact `(TypeError, "fqn.lastIndexOf is not a function") ↔ (Error, "a $class that is
not a string: …")` pair, and `bin/fuzz.js`/`bin/triage.js` exclude it before a case is
ever counted as an unresolved divergence — it is written to
`results/expected-divergences.jsonl` instead. Rust also gained two tests pinning the
message (`instance::serializer::tests::a_non_string_class_on_the_document_is_an_explicit_error`,
`..._a_non_string_class_on_a_nested_field_is_an_explicit_error`).

Representative seed: `data/Serializer.fromJSON/05598770d4c6f12c4d5dcf8e.json`,
mutationSeed 29. **Minimised** (`results/triage-clusters.json` — before the fix below
split it out of the file): all 7 of T1's true clusters reduce to a single edit,
`{"kind":"set","path":["$class"],"value":<true|1|-1|NaN|...>}`.

**Correction (this revision):** the previous revision of this file said "all 98
[what it called T1] clusters reduce to a single edit" and attributed all 98 to #156.
Both were wrong once re-checked against the narrow #156 match: only **7** clusters
(1,694 divergences) are this crash, and all 7 do reduce to 1 edit. The other 91
clusters the previous revision folded into "T1" are a different bug — see T1b.

### T1b — `Serializer.fromJSON`: a non-crashing, non-string `$class` (array/object), plus one outlier (1,060 divergences, owned by new issue #160)

**Not the same bug as T1**, discovered while implementing #156's harness change: when
a mutated `$class` is an **array** (e.g. `["org.test@1.0.0.C"]`), TS does *not* crash,
because `Array.prototype.lastIndexOf` also exists — it searches for an *element* equal
to `'.'`, finds none, returns `-1`, and `getShortName` returns the array itself
unsliced. That array is later stringified into a plain string, and TS raises an
ordinary `TypeNotFoundException: Namespace is not defined for type "org.test@1.0.0.C"`
— a normal rejection, not a crash. Rust still rejects it up front with the same `a
$class that is not a string: …` as T1's crash case, so it still diverges, but against
a *different* TS outcome kind and message (`TypeNotFoundException`, not `TypeError`).
90 of T1b's 91 clusters are this shape (56 minimise to 1 edit, 31 to 2, 3 to 3 — this,
not T1, is where the previous revision's "34 clusters need 2-3 edits" review finding
actually belongs). The 91st cluster (1 divergence) is unrelated to `$class` entirely:
`ts=ok`, `rust=error(ValidationException)`, `"Expected value at path \`$.t\` to be of
type \`DateTime\`"` — a genuine correctness gap that the previous revision's per-op
clustering happened to lump in with T1 too.

**Owner: accordproject/concerto-rust#160 (new issue, filed this revision).** #156's
sign-off is scoped narrowly to the `TypeError`/crash signature
(`lib/expected-divergences.js`'s exact match) and explicitly does not cover this;
`bin/attribute-owners.js` now attributes T1b clusters to #160 per-cluster (not via the
op-level `OWNERS` table, which would otherwise wrongly point every
`Serializer.fromJSON` cluster at the same place — see its `clusterOverride`).

### T2 — `ModelManager.fromAst`/`addModelFile`: AST deserialisation and validation gaps (2,494 divergences: 1,629 + 865, unchanged this revision)

This is the largest theme by distinct clusters, and the one with real correctness
content: cases where **TS accepts a mutated AST that Rust rejects**, and a handful the
other way. Sub-patterns, all inside `model_manager.rs`/the `introspect/*` modules that
`accordproject/concerto-rust#144` (P2-08c, **closed** — see this section's "Owner"
paragraph below for its exact status and why that doesn't settle T2 by itself) already
named as the root cause of a materially identical failure class found by direct corpus
traversal (`ModelManager.fromAst` (21), `addCTOModel` (56), `validateModelFiles` (21)):

- **Rust's serde AST deserialisation is stricter than TS's untyped-JS walk.**
  `invalid type: integer, expected a string`, `missing field 'pattern'`,
  `invalid type: string "…", expected struct StringLengthValidator`, `invalid type:
  boolean, expected f64` — TS happily loads a model whose numeric/string-typed AST
  field holds the "wrong" JS type (and fails later, if at all, with a different
  message or not at all); Rust's serde layer rejects it at parse time with a serde
  message that never goes through the TS-shaped error/message catalogue at all.
  **Owner: #144** (`introspect/property.rs`, `scalar.rs`, `validation.rs` — exactly
  the files #144 names).
- **Unguarded field access on optional/nullable AST fields in the wasm glue or
  Rust view code:** `this.name.toString is not a function`,
  `this.ast.identified.name.toString is not a function`, `Cannot read properties of
  undefined (reading '…')`, `Cannot read properties of null (reading '…')`. TS
  accepts (or fails differently on) an AST with a missing/null `name`,
  `identified.name` etc.; Rust's glue calls `.toString()`/reads a field without a
  null check. **Owner: #144** (`introspect/model_file.rs` is explicitly named as a
  root-cause file there for a materially identical class).
- **The rarer "Rust too permissive" direction (14 cases across the run, of 5,248):**
  `ts=TypeError rust=ok` — `ModelManager.addModelFile` (12), `ModelManager.fromAst`
  (2) — where Rust accepts a mutated AST that TS's constructor/loader crashes on (a
  TS bug: an uncaught `TypeError` from a missing null-check, not a spec rejection).
  The representative case: TS raises `TypeError: Cannot read properties of null
  (reading 'name')` for a `RelationshipProperty` whose `type` is `null`, but Rust
  accepts it (`ok`). Seed: `conformance/ModelManager.addModelFile/005d5a23d5c0d57ce9dfb0a4.json`,
  mutationSeed 2183103348. **Owner: #144** (same `model_file.rs`/`property.rs`
  territory; flagged separately because it is the direction where Rust
  under-validates rather than over-rejects, worth its own test once #144 is fixed —
  the other 13 cases are `results/divergence-summary.json`'s `rust=ok` rows and
  share the same likely root cause, though this triage did not inspect each one).
- **Exception-class/message-text-only mismatches** where both sides reject the
  mutated AST but disagree on the exact `IllegalModelException`/`TypeError` wording
  (`Invalid property name` vs `Invalid field name`, `Duplicate decorator undefined`
  differences, etc.) — lower priority than the two above, same owner (#144's
  `validation.rs`).

**Owner (corrected this revision), through the ledger:** `ModelManager.fromAst`/
`addModelFile` and `ModelFile.fromAst` are `basemodelmanager.ts`/
`introspect/modelfile.ts` in `SEAM_LEDGER.tsv`, `planned_task` `P2-08+P4-08`. Four
tasks carry that planned_task; two are the ones the coordinator asked this triage to
flag by name:
- **P2-08 (#52, closed)** — the base port.
- **P2-08b (#129, closed).** Its scope was the *other* `BaseModelManager`/`ModelManager`
  members the ledger gives P2-08 but that #52 left unported —
  `validateModelFile`/`updateModelFile`/`deleteModelFile`, `getModels`, `filter`,
  `resolveType`, `derivesFrom` — **not** `fromAst`/`addModelFile`. **No T2 cluster is
  owned by #129**; it is flagged here only because the coordinator named it explicitly.
- **P2-08c (#144).** Its scope was exactly T2's stack traces:
  `introspect/property.rs`, `scalar.rs`, `model_file.rs`, `validation.rs`, targeting
  the ~95 `ModelManager.addCTOModel`/`fromAst`/`validateModelFiles`/`ModelFile.new`
  oracle failures those files caused. **#144 closed (`completed`) at
  2026-09-25T17:11:00Z** — the previous revision of this file called it "open"; it
  had in fact just merged, about 90 seconds before that revision was posted (the fuzz
  run and WASM build this triage uses predate the merge). **This triage has not
  re-run against post-#144 Rust**, so it cannot say how many of these 311 clusters
  #144 already fixed versus how many are new correctness gaps fuzzing found that
  direct corpus traversal didn't (the `RelationshipProperty.type: null`
  under-validation case below is one candidate for the latter, since the corpus never
  records an invalid `RelationshipProperty` by construction). **Re-running this
  harness against current `claude/tender-pascal-ocwf9q` is the concrete next step**,
  not assumed here.
- **P4-08 (#67, open).** Scope: convert `ModelFile` and `BaseModelManager` —
  explicitly including `addModel(s)`, `validate`, `validateAst` — to thin TS views
  over the Rust core, depending on P2-08c (#144). Its own exit condition is that "the
  group's B tests **and oracle fixtures** pass with `CONCERTO_ENGINE=rust`" — T2's
  clusters are exactly the kind of oracle-fixture divergence that condition covers, so
  **#67 is T2's live open owner**: whatever #144 didn't already fix, #67's own exit
  bar requires it to fix (or document) before #67 can close.

So T2 is *not* down to one clean owner: #144 (closed) did the root-cause work these
stack traces point at, but is unverified against these exact fuzz-found clusters, and
#67 (open) is where any residual gap has to be caught, since its exit condition is
oracle-fixture parity under the Rust engine. Both are recorded as T2's owner in
`results/triage-clusters.json` (`bin/attribute-owners.js`).

## What this triage does not do

- **No product code is fixed**, other than the DV-015 sign-off itself (a test
  addition, not a behaviour change — Rust's rejection was already there; #156 decided
  to keep it, not to change it). Per the coordinator's stage-1 scope, remaining
  product-code fixes stay with the owning tasks named above (T1b: #160, new; T2:
  #144 closed / #67 open).
- **The corpus and `baseline.tsv` are untouched**, as instructed.
- **Not every individual divergence was manually inspected** — minimisation
  (`bin/minimize-clusters.js`) re-verifies each cluster's *sample* still reproduces
  its exact signature and shrinks it, but does not re-inspect the other 4,839
  divergences a cluster's `count` summarises, beyond the T2 "Rust too permissive" case
  singled out above. A cluster count is not a severity ranking by itself (a common,
  low-severity message-text mismatch can outnumber a rare correctness gap), which is
  why T2's sub-patterns are called out by kind, not just by count.
- **This triage was not re-run against current `claude/tender-pascal-ocwf9q`.** #144
  (P2-08c) merged about 90 seconds before the previous revision of this file was
  posted, so T2's 311 clusters may already be partly fixed — see T2's owner section.
  Re-running `bin/fuzz.js` against a fresh WASM build is the way to find out, not
  assumed here (out of stage 1's scope; stage 2 is where the full re-run happens
  anyway).
- **Stage 2 (the 1,000,000-case run) has not been attempted.** At the throughput
  measured in this run (see `results/run-42.json`'s `started`/`finished`), it is a
  multi-hour single-core job; per the coordinator, it belongs after #144/#67 (and
  #156's T1 decision) land, sharded or parallelised.
