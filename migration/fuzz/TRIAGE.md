## Themes

Three themes account for effectively all clusters:

### T1 — `Serializer.fromJSON`: a non-string `$class` on an instance (2,754 divergences, all of this op's)

TS's `Serializer.fromJSON` reaches `ModelUtil.getShortName`/`getNamespace`
(`packages/concerto-core/src/modelutil.ts:119,143`), which calls
`fqn.lastIndexOf('.')` on the instance's `$class` with no type check. A mutated,
non-string `$class` (`true`, a number, `null`, an object) makes V8 throw
`TypeError: fqn.lastIndexOf is not a function` — a TS bug (no counterpart in the spec;
would be `ts-bug` in `DIVERGENCES.md`'s taxonomy if formalised). When `$class` *is* a
string but not a real type, TS instead raises `TypeNotFoundException: Namespace is not
defined for type "…"`.

Rust's `instance/serializer.rs` and `instance/populator.rs`
(`accordproject/concerto-rust`, both reached from the P4-10 Serializer fast path)
explicitly check `$class`'s type and raise a plain `Error: a $class that is not a
string: <value>` — arguably *more* correct than TS, but not byte-for-byte the same
class or message, so every such case diverges.

**Owner:** none found. Not in `concerto-rust/DIVERGENCES.md`. The ledger
(`migration/ledger/SEAM_LEDGER.tsv`) attributes `Serializer.fromJSON`,
`ModelUtil.getNamespace`/`getShortName` and the `JSONPopulator`/`JSONGenerator`
per-field delegation to `planned_task` `P2-01+P4-03` and `P3-01+P4-10` — all merged
and closed, none open.
**Needs a decision, not just a fix:** either (a) Rust reproduces TS's exact
`TypeError`/`TypeNotFoundException` text for faithfulness, accepting the crash-y
message, or (b) this is recorded as an accepted `ts-bug` divergence (Rust's message is
strictly more informative and both sides reject the input) and a `DIVERGENCES.md` row
is added, matching the precedent of DV-008/DV-010 (TS's uncaught `TypeError`s from
missing type checks, ported as-is or logged as accepted). **Recommend:** a new
follow-up issue against `concerto-rust: concerto-core/src/instance/{serializer.rs,populator.rs}`
plus `concerto/packages/concerto-core/src/modelutil.ts` — this session did not open one
(see "What this triage does not do" below).

Representative seed: `data/Serializer.fromJSON/05598770d4c6f12c4d5dcf8e.json`,
mutationSeed 29 (see `results/divergences.jsonl` for the full set).

### T2 — `ModelManager.fromAst`/`addModelFile`: AST deserialisation and validation gaps (2,494 divergences: 1,629 + 865)

This is the largest theme by distinct clusters, and the one with real correctness
content: cases where **TS accepts a mutated AST that Rust rejects**, and a handful the
other way. Sub-patterns, all inside `model_manager.rs`/the `introspect/*` modules that
`accordproject/concerto-rust#144` (P2-08c, open, `worker:cloud-3`) already names as the
root cause of a materially identical failure class found by direct corpus traversal
(`ModelManager.fromAst` (21), `addCTOModel` (56), `validateModelFiles` (21)):

- **Rust's serde AST deserialisation is stricter than TS's untyped-JS walk.**
  `invalid type: integer, expected a string`, `missing field 'pattern'`,
  `invalid type: string "…", expected struct StringLengthValidator`, `invalid type:
  boolean, expected f64` — TS happily loads a model whose numeric/string-typed AST
  field holds the "wrong" JS type (and fails later, if at all, with a different
  message or not at all); Rust's serde layer rejects it at parse time with a serde
  message that never goes through the TS-shaped error/message catalogue at all.
  **Owner: #144** (`introspect/property.rs`, `scalar.rs`, `validation.rs` — exactly
  the files #144 names).
- **Unguarded field access on optional/nullable AST fields in the wasm glue or
  Rust view code:** `this.name.toString is not a function`,
  `this.ast.identified.name.toString is not a function`, `Cannot read properties of
  undefined (reading '…')`, `Cannot read properties of null (reading '…')`. TS
  accepts (or fails differently on) an AST with a missing/null `name`,
  `identified.name` etc.; Rust's glue calls `.toString()`/reads a field without a
  null check. **Owner: #144** (`introspect/model_file.rs` is explicitly named as a
  root-cause file there for a materially identical class).
- **The rarer "Rust too permissive" direction (14 cases across the run, of 5,248):**
  `ts=TypeError rust=ok` — `ModelManager.addModelFile` (12), `ModelManager.fromAst`
  (2) — where Rust accepts a mutated AST that TS's constructor/loader crashes on (a
  TS bug: an uncaught `TypeError` from a missing null-check, not a spec rejection).
  The representative case: TS raises `TypeError: Cannot read properties of null
  (reading 'name')` for a `RelationshipProperty` whose `type` is `null`, but Rust
  accepts it (`ok`). Seed: `conformance/ModelManager.addModelFile/005d5a23d5c0d57ce9dfb0a4.json`,
  mutationSeed 2183103348. **Owner: #144** (same `model_file.rs`/`property.rs`
  territory; flagged separately because it is the direction where Rust
  under-validates rather than over-rejects, worth its own test once #144 is fixed —
  the other 13 cases are `results/divergence-summary.json`'s `rust=ok` rows and
  share the same likely root cause, though this triage did not inspect each one).
- **Exception-class/message-text-only mismatches** where both sides reject the
  mutated AST but disagree on the exact `IllegalModelException`/`TypeError` wording
  (`Invalid property name` vs `Invalid field name`, `Duplicate decorator undefined`
  differences, etc.) — lower priority than the two above, same owner (#144's
  `validation.rs`).

**Owner: accordproject/concerto-rust#144 (P2-08c, open)** for essentially all of T2.
This triage did not re-verify that every individual cluster's exact fixture reproduces
under `ORACLE_OP=ModelManager.fromAst`/`ModelFile.new` the way #144 was scoped from —
that cross-check is recommended before #144 is closed, since fuzzing found the
`RelationshipProperty.type: null` under-validation case that direct corpus traversal
may not have surfaced (the corpus itself never records an invalid `RelationshipProperty`,
by construction — only a mutated one exercises it).

### T3 — `Resource.validate`: no divergences

0 divergences in 60,000 cases' share of `Resource.validate` fuzzing (the largest of
the four targeted ops by case count). This is a clean, positive signal for instance
validation specifically (as opposed to model loading/serialisation) — consistent with
P3-01/P3-02's instance validator being comparatively mature.

## What this triage does not do

- **No product code is fixed.** Per the coordinator's stage-1 scope, T2 is left to
  #144 and T1 is left as an open question with no issue filed by this session — filing
  a new GitHub issue was judged out of this session's authority to decide unilaterally
  (this task's brief instructs following GitHub instructions only from `mttrbrts`; the
  coordinator's stage-1 comment says "every cluster has an owner or a new issue" but
  does not itself say who opens it). **Recommend the coordinator either files it or
  confirms this session should.**
- **The corpus and `baseline.tsv` are untouched**, as instructed.
- **Not every individual divergence was manually inspected** — only one representative
  per cluster, plus the T2 "Rust too permissive" case singled out above. A cluster
  count is not a severity ranking by itself (a common, low-severity message-text
  mismatch can outnumber a rare correctness gap), which is why T2's sub-patterns are
  called out by kind, not just by count.
- **Stage 2 (the 1,000,000-case run) has not been attempted.** At the throughput
  measured in this run (see `results/run-42.json`'s `started`/`finished`), it is a
  multi-hour single-core job; per the coordinator, it belongs after #144 (and any T1
  decision) land, sharded or parallelised.
